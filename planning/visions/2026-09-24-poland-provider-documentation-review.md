# Poland provider documentation review

## Outcome

Revise the existing Poland provider documentation PR [#291](https://github.com/RivRetrieve/RivRetrieve/pull/291) so its page and PR description describe RivRetrieve as it works now. The PR predates the provider and API changes in [#300](https://github.com/RivRetrieve/RivRetrieve/pull/300). This is a correction of the documentation itself, not a migration guide: readers have no legacy usage to support. Preserve Thiago's accurate work where possible.

The resulting page should help a hydrologist understand Poland's national source, who measures and publishes the observations, what RivRetrieve retrieves, and how to interpret a practical example. It should not become a mechanical API reference or a record of the documentation migration. Update the existing PR rather than opening a replacement implementation PR. The PR description must accurately summarize the revised page and its verification.

## Reader-facing content

Follow `docs/AGENTS.md` as mandatory writing guidance. Use the merged `docs/providers/` pages, particularly their introductory tables and practical examples, as strong references. Keep corresponding table entries consistent across provider pages. Explain source-specific coverage, units, dates and time zone, availability, data status, access preparation, and terms where they affect interpretation. Link to the general usage guide for general API instruction. Preserve source vocabulary and explicit unknowns; distinguish an absent observation from a null source cell and from a request or local-store failure where applicable. Do not infer source quality, statistical meaning, day boundaries, or geographic or temporal coverage from a catalogue listing.

For Poland specifically, investigate the current packaged catalogue and code rather than copying #291's prior assumptions. The current source products are `discharge_daily`, `stage_daily`, and `water_temperature_daily`; the catalogue records daily frequency but does not establish a common `mean` statistic. Current `rr.find` does not take `product=`. The draft's `*_daily_mean` IDs and product-based selection are obsolete. Its English-labelled “IMGW column” headings also need comparison with the publisher's actual Polish field labels. The packaged station inventory contains 1,301 stations; listed series availability is unknown. The provider explicitly prepares a bulk local archive before retrieval, and stage is converted from centimetres to metres. Verify these and any other claims against the implementation, catalogue, and publisher before retaining them. The existing page's GRDC coordinate provenance and unknown CRS/time-zone statements need the same check. Avoid giving the reader catalogue-evidence machinery unless it clarifies a practical limitation.

IMGW-PIB's published regulations require careful, accurately attributed treatment: distinguish the agency's free-use conditions from business use and other specified uses, and retain the prescribed source attribution and, when the data are processed, the additional processed-data statement with appropriate Polish wording and clearly marked unofficial translation. Describe limitations without offering new legal conclusions; link to the full authoritative regulations. Explain that the publisher warns some data may be unverified without RivRetrieve assigning a quality grade. Check claims about IMGW-PIB's measurement and publication roles against authoritative sources.

## Verification and delivery

Check every factual claim against current code, the packaged catalogue, or authoritative publisher material. Run **every code snippet** against the current public API. Use live retrieval where applicable, including the page's practical example, and verify the displayed output and promised behavior. Distinguish live retrieval evidence from recorded tests. If source values or archive editions can change, present a verified dated example with an appropriate qualification rather than implying permanent numerical identity. An example must be executable as printed, including its setup and cache prerequisites, and explain the reader-visible result and issues. Do not claim a successful live check from a recorded fixture.

The intended deliverable is the updated existing PR #291: revised documentation (including its index entry as needed) and an accurate PR description. The human reviews the PR and gives feedback **before the implementation agent concludes**. Do not approve or merge #291 on the human's behalf. This review gate applies to the implementation PR, not to this vision's separate publication PR.

If implementation uncovers a **production-code defect**, stop the documentation work. Open an issue labelled `bug`, assign it to `CooperBigFoot`, and include reproduction steps and evidence, using [#305](https://github.com/RivRetrieve/RivRetrieve/issues/305) and [#324](https://github.com/RivRetrieve/RivRetrieve/issues/324) as examples. Do not repair production code within this vision and do not conceal a defect through documentation changes. Wait until the human reports a repair; then reverify and continue. A documentation mismatch alone is not a production-code defect.

## Boundaries

Do not implement new provider behavior, rewrite unrelated provider pages, publish a migration narrative, or merge the implementation PR. Do not turn unresolved source facts into invented defaults. The final documentation must describe the code and source that actually exist when the implementation is verified, even if the upstream service later changes.
