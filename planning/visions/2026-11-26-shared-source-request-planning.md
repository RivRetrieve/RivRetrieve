# Shared source request planning

RivRetrieve should plan source requests for a whole live provider selection. Bulgaria’s NIMH publishes one CSV per day containing stage and discharge for 68 stations. Reading all 68 stations over 30 available dates should take 30 downloads and 30 file decodes when the store is empty and every request succeeds on its first attempt. The station-by-station path described by the port would issue 2,040 GETs for the same files. Implementation of this vision completes [#1076](https://github.com/RivRetrieve/RivRetrieve/issues/1076). The Bulgarian port has its own [scope decision](https://github.com/RivRetrieve/RivRetrieve/issues/1065#issuecomment-7167061438) and [final review](https://github.com/RivRetrieve/RivRetrieve/issues/1072).

## 1. Give the core engine the whole request

At the [audited revision](https://github.com/RivRetrieve/RivRetrieve/tree/b2697ec8025f56669c4b97316876fcccce2cdd79), public `rr.fetch` groups a selection by station, calls the provider handle once per station, then merges the results. The driver checks store reuse per station and product, groups some products with compatible bounds, and passes one station to the fetch stage. Changing the grouping predicate alone would leave the public path split. Existing payloads can already name several station–product pairs, grouped parsing can return an answer for each pair, and one acquisition can support several outcomes. [Public composition](../../src/rivretrieve/_internal/discovery.py) · [Driver](../../src/rivretrieve/_internal/driver.py) · [Stage contracts](../../docs/architecture.md)

Keep the exact set of consumers through planning. For example, a caller requests stage and discharge at A and B. The store can serve A’s discharge and B’s stage. Only A’s stage and B’s discharge need fresh answers. A shared file may contain all four. Only the two outstanding pairs may acquire fresh observations, coverage and retrieval times. The same rule applies to explicit series restrictions and to selections that contain different products at different stations.

The engine should decide which work is necessary, share downloads and prerequisite lookups, form supported batches, route the resulting payloads or decoded rows to their consumers, and account for success or failure. Providers specify what identifies a file, which lookups locate it, which selectors can travel together, what limits apply, how to construct a native request, and how to interpret the returned identities, values, pagination and errors. Put reusable planning and bookkeeping in the engine. Introduce a shared capability when multiple real providers need it. Keep a quirk confined to the provider that owns it.

A clean rewrite of the station-first orchestration and provider contracts is welcome. Breaking changes are expected and accepted. Remove superseded paths and update callers, tests and documentation together. Choose the representation during implementation. Source request identity must account for the actual operation, including relevant parameters, body, bounds and access context. Repeated URLs can describe different observations, retries or refreshes.

### Sharing files and building batches

A shared file already exists in the same form for all its consumers. A batch combines distinct selectors into a request the publisher supports. Both belong in the core design. A batch can add pages, exceed a response limit or return only some selected series. The engine needs the complete response chain before a missing series can count as an exhaustive empty answer. Route each returned block by established source identity, including when blocks arrive out of order.

Use Hub’Eau and Norway to ground the batching design. Hub’Eau accepts up to 100 station or site codes for daily hydrometry and 200 station codes for temperature. Norway accepts station lists and can describe individual series in an observation POST. Verify benefit on representative selections and equivalent results before enabling batching for a route. Count requests including pages, retries and subdivisions. Compare elapsed time and bytes, and exercise partial failures. Choose batch sizes based on the observed workload within the publisher’s limits. [Hub’Eau hydrometry](https://hubeau.eaufrance.fr/api/v2/hydrometrie/api-docs) · [Hub’Eau temperature](https://hubeau.eaufrance.fr/api/v1/temperature/api-docs) · [NVE HydAPI](https://hydapi.nve.no/UserDocumentation/)

## 2. Migrate providers where the shared design helps

Use Bosnia, the Bulgarian daily-file case and a Hub’Eau batch to exercise the design through public retrieval while developing it. The Bulgarian port was awaiting final review at the audited revision. Exercise its source shape through a synthetic provider when working ahead of the port, and coordinate adoption against its reviewed integration. Keep its source admission and merge decision with the port maintainers.

The audit covered all 17 registered live providers. Offline counting transports on the actual engine established the following baselines. Counts refer to the selections shown with an empty or bypassed store and one attempt per request. They count calls made through the transport.

| Provider | Current work and migration target |
| --- | --- |
| Bosnia `ba_fhmzbih` | Public retrieval of two stations and three products made 12 calls and retained 12 receipts. Six calls downloaded the same station index. Fetch the index once and the six workbooks separately. An unresolvable index entry at A must still allow B’s workbook to succeed. |
| Norway `no_nve` | Unrestricted stage at three resolutions looked up the same station/parameter inventory three times. Fetch it once and derive three scoped inventories. Keep observation requests specific to the selected versions and resolutions unless a supported batch serves them. Explicit version selections can skip the lookup. |
| Czechia `cz_chmi` | Five products at one station in one year read the daily file three times and the hourly file twice. Fetch and decode each file once. Align the parser’s native series checks with exact pair ownership. The existing [engine receipt test](../../tests/test_cz_chmi_observations.py) records the duplicate baseline. |
| Thailand `th_thaiwater` | Stage and discharge at one station use the same graph for a compatible span. Two GETs can become one. Other stations use other request parameters. The [public retrieval test](../../tests/test_lt_lhmt_th_thaiwater_public.py) covers this distinction alongside Lithuania. |
| Brazil `br_ana` | Six products at one station over compatible spans issued six GETs for three requests. Telemetry stage and discharge share a response. Daily stage and daily discharge each publish their own Bruto and Consistido variants together. Preserve each variant’s identity and annotations, and isolate malformed fields to the affected variant. |

Australia already combines some series IDs. Its station lookup and values API support lists. Switzerland supports multi-station filters. FOEN can reject large responses, triggering window subdivision in RivRetrieve. Evaluate these routes where batching offers a benefit. USGS recommends smaller queries for some workloads, Finland’s OData paging and station attribution need evidence, and Argentina’s alternative series-list endpoint needs an equivalence check for boundary nulls. Each candidate needs evidence of a benefit on its observation route. [Australia’s verified retrieval behaviour](2026-11-03-au-bom-retrieval-behavior.md) · [Swiss filters](https://data.bafu.admin.ch/en/filter-und-operatoren) · [USGS query guidance](https://api.waterdata.usgs.gov/docs/ogcapi/complex-queries/)

Use Lithuania, Peru and Austria as controls for existing station-specific product and prerequisite sharing. Colombia’s objects are keyed by station and product. Denmark has station-specific routes and already extracts both stage fields from one response. HydroPortail requests distinct publication-status streams. Carry these providers through any interface changes and preserve their source boundaries. Reconcile the live-provider list with the implementation branch before landing. Bulk compilation and catalogue discovery use separate acquisition paths.

## What proves the refactor works

- Exercise public `rr.fetch` with a cold store, mixed hits and misses, a fully reusable selection, bypass and refresh. Check actual calls and decode counts alongside exact observations, source facts, annotations, inventories, coverage and outcomes. Preserve each consumer’s padded and rendered bounds, clipping semantics and selectors.
- Exercise a missing whole bulletin, an unmeasured value or malformed field at one station, a missing prerequisite entry, and a failed late page. Keep successful siblings and independent dates. Preserve the distinctions among a null value, an absent row, a proven empty result and a failed request. Failed refreshes retain held successes at their original retrieval time. Invalid internal stage output remains fatal.
- Record one actual acquisition with its true consumers and prerequisite links. Preserve distinct attempts and later acquisitions of the same URL. Check exact publisher bytes with receipts enabled, call provenance with receipts omitted, and original acquisition times and correctly labelled store-excerpt receipts on reread. The [combined review of #938](https://github.com/RivRetrieve/RivRetrieve/pull/999) found duplicated call evidence and a sibling failure contaminating inventory reconciliation. Repeat those checks across stations.
- Use focused synthetic tests for sparse selections, work counts and failure isolation. Run the applicable genuine-input replay and evidence checks for affected provider routes under the [maintainer evidence guide](../../docs/maintenance/evidence.md). Report measured batching benefits and limits separately from deterministic reductions in duplicate calls.

Review the core contract with representative providers end to end, then review adoption against the same guarantees. [The #992 review sequence](https://github.com/RivRetrieve/RivRetrieve/issues/992#issuecomment-7136701149) provides a precedent. A second provider with the same capability should need to describe its source and interpret its responses without implementing another planner.
